{% load i18n icons %} {% comment %} One "Your Performance" summary card (TASK-25). Rendered both inline, once per lift, inside detail.html's Summary tab grid, and standalone as the htmx response of manual_lift_view (challenges:manual-lift) — the latter swaps outerHTML onto exactly this card's own #summary-card- wrapper, so the markup here must always be a single complete replacement for itself, never a sub-fragment that assumes surrounding context is already in the DOM. Two faces share one card: the front is the existing read-only summary (state scored/no_points/no_data_before_window/no_data), the back is the self-report carousel. Both are present in the DOM whenever self-report is available (see can_self_report below); only a CSS class ("is-flipped") on the outer wrapper picks which one shows (challenges/detail.html's flip-card CSS + initManualLiftCard()), so JS never has to fetch anything to flip. The card always renders on its front face -- there is no server-rendered flipped state, because a submission that would leave the lifter on the back (nothing gained) is refused before it gets here (challenges.services submit_manual_lift). Flipping is purely a client interaction. can_self_report gates the whole self-report half of the card: when false (a COMPLETED/CANCELLED challenge -- see challenge_detail_view) the back face, the flip affordance, the flip-card CSS classes and the data-* attributes that wire the JS are all omitted, leaving a plain static summary. The classes have to go with it, not just the button: .flip-card-front is absolutely positioned and .flip-card gets overflow:hidden, so a card whose JS never runs to size .flip-card-inner would collapse to zero height and render blank. challenge.is_terminal separately re-words the FRONT face: every gap line here ("add X to reach your first point") is a nudge toward a lift the challenge can still score, so on a finished challenge each one is restated in the past tense ("finished X short of ..."). The number itself is unchanged -- only its framing is -- so the lifter keeps the "how close was I" context without being told to act on a locked challenge. It is read off `challenge` rather than inverting can_self_report because the two answer different questions: this fragment is also the htmx response of manual_lift_view, which only ever renders it for a live challenge but passes can_self_report explicitly. `close_to_goal` needs no branch here -- _flag_close_to_goal declines to set it at all on a terminal challenge (challenges.services).
