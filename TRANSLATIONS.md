# Translating very lift

The app supports translation via Django's standard gettext `.po`/`.mo` workflow.
Each supported language lives in its own `locale/<code>/LC_MESSAGES/django.po` file,
independent of every other language — you can translate one language start to
finish without touching anyone else's work, and without needing to translate the
whole app in a single sitting.

## What's already translated

- **Supported languages**: the `LANGUAGES` list in `root/settings.py`. Only
  languages listed there are selectable in the app's language switcher
  (Settings → Language), regardless of whether a `locale/` directory exists for
  them.
- **In-progress / claimed languages**: check open issues and PRs labeled
  [`translation`](https://github.com/verylift/verylift/issues?q=label%3Atranslation)
  on GitHub before starting, to avoid duplicating someone else's work. Open an
  issue labeled `translation` naming the language you want to work on to claim it.
- **Completeness of an existing catalog**: run `msgfmt --statistics
  locale/<code>/LC_MESSAGES/django.po` (part of the `gettext` package). It reports
  translated / fuzzy / untranslated counts. A complete, mergeable catalog has zero
  fuzzy and zero untranslated entries.

## Adding a new language

1. Install the `gettext` system package (provides `msgfmt`/`msguniq`/`xgettext`,
   used by `manage.py makemessages`/`compilemessages`):

   ```bash
   sudo apt-get install gettext
   ```

2. Add the language to `LANGUAGES` in `root/settings.py`, using its
   [ISO 639-1 code](https://en.wikipedia.org/wiki/List_of_ISO_639_language_codes)
   and its name written in that language itself (matching the existing `en`/`es`
   entries — language names are deliberately not translated):

   ```python
   LANGUAGES = [
       ("en", "English"),
       ("es", "Español"),
       ("fr", "Français"),  # new
   ]
   ```

   No database migration is needed for this step — `User.language` is a plain
   `CharField` with no `choices` kwarg on purpose, precisely so that adding a
   language here never requires one.

3. Generate the `.po` file for your language code:

   ```bash
   just makemessages fr
   ```

   This scans every template and Python source file for `{% trans %}`,
   `{% blocktrans %}`, `gettext`, and `gettext_lazy` usages and writes (or updates)
   `locale/fr/LC_MESSAGES/django.po` with one `msgid`/`msgstr` pair per string,
   each annotated with the source file/line it came from.

4. Translate every `msgstr ""` line in the `.po` file. A few rules:
   - Leave `msgid` untouched — it's the English source key, not something you edit.
   - Preserve every `%(name)s`-style placeholder and embedded HTML tag
     (`<strong>…</strong>`, `<span class="...">…</span>`) exactly — they're
     substituted or rendered at runtime, not literal text to translate.
   - Entries with `msgid_plural` need both `msgstr[0]` (singular) and `msgstr[1]`
     (plural) filled in, following your language's own plural rules — not
     English's. Update the `Plural-Forms` header at the top of the file to match
     your language ([cheat sheet](https://www.gnu.org/software/gettext/manual/html_node/Plural-forms.html))
     if it differs from the default two-form English rule.
   - Don't mark entries `#, fuzzy` (or leave that flag on an autogenerated fuzzy
     match) — a fuzzy entry is silently skipped at runtime, which reads to a user
     as "half the app is untranslated."

5. Compile the catalog:

   ```bash
   just compilemessages
   ```

   This turns every `locale/*/LC_MESSAGES/django.po` in the repo into a binary
   `.mo` that Django actually loads at runtime — `.po` alone has no effect on the
   running app. Re-run this any time you edit a `.po` file.

6. Verify locally: run the dev server (`just serve`), sign in, go to
   Settings → Language, and select your language. Click through the app's main
   pages (dashboard, a challenge, notifications, settings) to sanity-check
   rendering — long translated strings occasionally break layout in ways a
   msgid-by-msgid read won't catch.

7. Run `just ci` (lint + format + tests) before opening a PR.

8. Open a PR that **commits both `locale/<code>/LC_MESSAGES/django.po` and the
   compiled `django.mo`**. The `.mo` is a generated binary, but this repo commits
   it deliberately (matching the existing precedent for `static/css/output.css`
   and the vendored JS in `static/vendor/`): the dev container and the production
   Dockerfile have no `gettext` toolchain, and there's no guarantee `msgfmt` is
   installed on whatever runs CI either. Committing the compiled catalog means
   the translation ships correctly regardless of what's installed on the
   machine that builds the image.

## Updating an existing translation

Same flow as adding a language, minus step 2 (the language is already in
`LANGUAGES`) — run `just makemessages <code>` to pick up any new or changed source
strings (existing translations are preserved; only new/changed `msgid`s appear as
untranslated), translate the new entries, `just compilemessages`, and PR both
files.

## Reviewing an existing translation

Native-speaker review PRs are very welcome, including for the Spanish pilot
catalog (`locale/es/`), which was produced by the implementer rather than a native
speaker. Same workflow: edit the `.po`, recompile, PR.

## What isn't translatable yet

A few content surfaces are out of scope for the gettext-based workflow above and
are tracked as separate follow-up work rather than silently left half-done:

- **Legal pages** (`templates/legal/terms.html`, `templates/legal/privacy.html`) —
  translating ~450 lines of Terms of Service / Privacy Policy text is a
  legal/product decision (accuracy of a translated legal document carries real
  liability), not a mechanical string-wrapping task.
- **User guide content** (`docs/*.md`, rendered by the `guide` app) — the guide's
  page titles and chrome *are* translatable (they go through gettext), but the
  markdown body content is not; it needs a per-language-file design (e.g.
  `docs/scoring.es.md`) that hasn't been built yet.
- **Seeded lift names** (e.g. "Bench Press") — these are database rows from
  `liftosaur`/`fitnessvolt` seed data, not code strings, so they're outside
  gettext's reach entirely.
- **Dates** — templates use explicit `|date:"M j, Y"`-style formats, which stay in
  that (English-ordered) form regardless of the active language. Locale-aware date
  formatting is a separate piece of work.
- **IANA timezone identifiers** (e.g. "America/Toronto", shown in the settings
  timezone picker) are identifiers, not prose — they stay in their canonical
  English form in every language.
- **The custom-goal AI prompt** (the "Copy AI prompt" button on the custom-goal
  setup page) generates an English-language prompt meant to be pasted into an LLM
  chat. It's left in English deliberately — the prompt's JSON-schema instructions
  need to stay unambiguous for the LLM regardless of the UI's display language.
